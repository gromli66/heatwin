# ЧАСТЬ 1: CRISP-DM (91 стр.)

## I. Введение в методологию (стр. 1–5)

### Иерархическая структура (4 уровня)

CRISP-DM описывает процесс data mining как иерархию из 4 уровней:

1. **Фаза (Phase)** — верхний уровень. 6 фаз.
2. **Общая задача (Generic Task)** — задачи внутри фазы. Универсальны для любого проекта.
3. **Специализированная задача (Specialized Task)** — конкретизация общей задачи для данного контекста (напр., очистка числовых vs категориальных данных).
4. **Экземпляр процесса (Process Instance)** — запись того, что реально произошло в конкретном проекте (решения, действия, результаты).

Важно: последовательность фаз НЕ строгая. Возвраты к предыдущим фазам — норма, не исключение. Модель не пытается охватить все возможные маршруты — это было бы слишком сложно.

### Reference Model vs User Guide

- **Reference Model** — краткий обзор: что делать (фазы, задачи, выходы)
- **User Guide** — детальные советы: как делать (активности, чеклисты, подсказки)

### Контекст data mining (4 измерения)

Каждый проект имеет контекст по 4 измерениям:
1. **Application Domain** — предметная область (маркетинг, телеком, теплоснабжение...)
2. **Data Mining Problem Type** — тип задачи (classification, prediction, segmentation...)
3. **Technical Aspect** — технические вызовы (пропуски, выбросы, масштаб...)
4. **Tool and Technique** — инструменты (Python, LightGBM, нейросети...)

Маппинг общей модели на конкретный проект: убрать неприменимое, добавить специфичное, конкретизировать, возможно переименовать для ясности.

## II. Reference Model — 6 фаз (стр. 6–40)

### Общая схема

Жизненный цикл проекта: 6 фаз, стрелки = частые зависимости, внешний круг = циклическая природа (проект не заканчивается деплоем — уроки ведут к новым вопросам).

```
Business Understanding ↔ Data Understanding
         ↓                       ↓
    Data Preparation ← → Modeling
              ↓              ↓
           Evaluation
              ↓
           Deployment
```

Данные — в центре. Три фазы (Data Understanding, Data Preparation, Modeling) постоянно обращаются к данным.

### Фаза 1: Business Understanding (стр. 9–14)

Фокус: понять цели и требования с точки зрения бизнеса, перевести в задачу data mining, составить план.

#### 1.1 Determine Business Objectives
**Задача:** Понять, что клиент РЕАЛЬНО хочет. Часто у клиента много конкурирующих целей и ограничений, которые нужно сбалансировать. Пропуск этого шага = «правильные ответы на неправильные вопросы».

**Выходы:**
- **Background** — информация о бизнес-ситуации организации на начало проекта
- **Business Objectives** — первичная бизнес-цель + связанные бизнес-вопросы. Пример: цель = удержать клиентов, вопросы = «влияет ли канал (ATM/интернет) на уход?», «снизят ли комиссии отток?»
- **Business Success Criteria** — критерии успеха с точки зрения бизнеса. Конкретные (снизить churn до X%) или субъективные (полезные инсайты — но тогда указать кто будет судить)

**Активности (из User Guide):**
- Организация: оргструктура, ключевые персоны, спонсор, стееринг-комитет
- Проблемная область: описание проблемы, текущий статус проекта, целевая аудитория результатов, потребности пользователей
- Текущее решение: описание, плюсы/минусы, уровень принятия пользователями
- Сформулировать бизнес-вопросы максимально точно
- Указать ожидаемые выгоды в бизнес-терминах
- **BEWARE:** не ставить недостижимые цели!

#### 1.2 Assess Situation
**Задача:** Детальное исследование ресурсов, ограничений, допущений. В 1.1 — суть проблемы быстро. Здесь — детали.

**Выходы:**
- **Inventory of Resources** — персонал (бизнес-эксперты, технические специалисты, data mining), данные (экстракты, live-доступ), hardware, software
- **Requirements, Assumptions, Constraints:**
  - Requirements: сроки, качество, безопасность, юридические вопросы, ПРАВО ИСПОЛЬЗОВАТЬ ДАННЫЕ
  - Assumptions: о данных (проверяемые) и о бизнесе (непроверяемые). Непроверяемые ОСОБЕННО важно записать — от них зависит валидность результатов
  - Constraints: ресурсы, технические ограничения (размер данных), доступ
- **Risks and Contingencies** — риски (бизнес, организационные, финансовые, технические, данные/источники) + планы B
- **Terminology** — два глоссария: бизнес-терминология и DM-терминология (с примерами из задачи). Составление глоссария = полезное упражнение по извлечению знаний
- **Costs and Benefits** — cost-benefit анализ, максимально конкретный (в деньгах). Учитывать скрытые затраты: повторная подготовка данных, изменение рабочих процессов, обучение

#### 1.3 Determine Data Mining Goals
**Задача:** Перевести бизнес-цели в технические. Пример: бизнес = «увеличить каталожные продажи», DM = «предсказать сколько товаров клиент купит, зная покупки за 3 года, демографию и цену».

**Выходы:**
- **Data Mining Goals** — технические цели, обеспечивающие бизнес-цели
- **Data Mining Success Criteria** — технические критерии успеха (точность, lift). Если субъективные — указать кто оценивает

**Активности:**
- Указать тип DM-задачи: classification, description, prediction, clustering
- Возможно переформулировать задачу (моделировать удержание продукта вместо клиента — может быть эффективнее!)
- **BEWARE:** DM Success Criteria ≠ Business Success Criteria
- **ПОМНИТЬ:** планировать деплой с самого начала

#### 1.4 Produce Project Plan
**Задача:** План достижения DM-целей → бизнес-целей.

**Выходы:**
- **Project Plan** — этапы, длительность, ресурсы, входы/выходы, зависимости, итерации. Динамический документ — пересматривается в конце каждой фазы. Включает точки review. Типичное распределение усилий: Data Preparation 50-70%, Data Understanding 20-30%, каждая из остальных фаз 10-20%, Deployment 5-10%
- **Initial Assessment of Tools and Techniques** — выбор инструментов. Важно сделать рано — выбор влияет на весь проект

### Фаза 2: Data Understanding (стр. 15–19)

#### 2.1 Collect Initial Data
**Задача:** Получить доступ к данным. Включает загрузку если нужно для инструмента. При нескольких источниках — интеграция = отдельная проблема.

**Выход:** Initial Data Collection Report — список данных, расположение, метод получения, возникшие проблемы и решения (для воспроизводимости).

**Активности:** Планирование требований к информации, критерии отбора (атрибуты, таблицы, объём истории), описание экстракции. Помнить: знания могут быть на нецифровых носителях. Может потребоваться предобработка.

#### 2.2 Describe Data
**Задача:** Исследовать «поверхностные» свойства данных.

**Выход:** Data Description Report — формат, объём (записи × поля), идентификация полей, поверхностные свойства.

**Активности:** Объёмный анализ (таблицы, связи, сложность), типы атрибутов (числовые, символьные, таксономии), диапазоны значений, корреляции, смысл каждого атрибута в бизнес-терминах, базовая статистика (распределения, среднее, min/max, стд. откл., дисперсия, мода, асимметрия), ключи, ревизия допущений.

#### 2.3 Explore Data
**Задача:** Исследовательский анализ — запросы, визуализация, отчёты. Распределения ключевых атрибутов, связи между парами атрибутов, агрегации, свойства подгрупп, простая статистика.

**Выход:** Data Exploration Report — первые находки, начальные гипотезы, их влияние на проект, графики.

**Активности:** Анализ свойств интересных атрибутов, характеристики подгрупп. Формулировка гипотез и перевод в DM-цели. Слепой поиск не бесполезен, но направленный поиск к бизнес-целям предпочтительнее.

#### 2.4 Verify Data Quality
**Задача:** Проверить качество: полнота, корректность, ошибки, пропуски (как представлены, где, частота).

**Выход:** Data Quality Report — результаты проверки, проблемы и возможные решения (зависят от знания данных И бизнеса).

**Активности:** Специальные значения (каталогизировать значения), ключи и атрибуты (покрытие, пропуски, противоречия), орфография значений, отклонения (шум или интересное явление?), правдоподобность, шум между источниками. ПОМНИТЬ: можно исключить нерелевантные данные.

### Фаза 3: Data Preparation (стр. 20–26)

Самая трудоёмкая фаза (50-70% усилий). Задачи выполняются многократно, не в строгом порядке.

**Общие выходы:** Data Set + Data Set Description

#### 3.1 Select Data
**Задача:** Выбрать данные для анализа. Критерии: релевантность, качество, технические ограничения. Покрывает выбор атрибутов (колонок) И записей (строк).

**Выход:** Rationale for Inclusion/Exclusion — список данных + обоснование каждого решения.

**Активности:** Тесты значимости и корреляции, пересмотр критериев по мере опыта, подвыборки, сэмплирование (уменьшение размера, взвешивание). Документировать обоснование.

#### 3.2 Clean Data
**Задача:** Повысить качество до требуемого уровня. Методы: чистые подмножества, дефолтные значения, оценка пропусков моделированием.

**Выход:** Data Cleaning Report — решения и действия по качеству, трансформации, влияние на результаты.

**Активности:** Работа с шумом, специальными значениями (99 = «неизвестно», 00 = обрезанное значение), пересмотр критериев. ПОМНИТЬ: шум в нерелевантных полях не имеет значения (но документировать!).

#### 3.3 Construct Data
**Задача:** Создание новых атрибутов и записей.

**Выходы:**
- **Derived Attributes** — из существующих (area = length × width). Зачем: фоновые знания подсказывают важный факт без существующего атрибута; алгоритм требует определённый тип данных; моделирование показало пробелы
- **Generated Records** — полностью новые записи (например, записи для клиентов без покупок — нет в raw данных, но важны для модели)

**Активности:** Нормализация, веса атрибутов, конструирование пропущенных (агрегация, среднее, индукция). Трансформации: дискретизация числовых в символьные, символьные в числовые. НЕ создавать производные атрибуты просто для уменьшения числа входных.

#### 3.4 Integrate Data
**Задача:** Объединение из нескольких таблиц/источников.

**Выход:** Merged Data — соединение таблиц (join) + агрегация (summarize). Пример: три таблицы (характеристики магазинов, продажи, демография) → одна таблица с одной записью на магазин.

#### 3.5 Format Data
**Задача:** Синтаксические модификации без изменения смысла, требуемые инструментом.

**Выход:** Reformatted Data — порядок атрибутов (первый = ID, последний = таргет), порядок записей (случайный для нейросетей, сортированный для других), синтаксические правки (удаление запятых, обрезка длины значений).

### Фаза 4: Modeling (стр. 27–31)

#### 4.1 Select Modeling Technique
**Задача:** Выбрать конкретную технику (C4.5, нейросеть с backprop...). Не все техники применимы ко всем задачам (см. Appendix V.2). Ограничения: инструмент, «политические» требования (понятность для менеджмента), время, данные, знания.

**Выходы:** Modeling Technique + Modeling Assumptions (требования к данным: распределения, пропуски, типы атрибутов). Сравнить допущения с Data Description. Если не выполняются — вернуться в Data Preparation.

#### 4.2 Generate Test Design
**Задача:** Определить процедуру тестирования качества модели. Типично для supervised: разделить данные на train/test, построить на train, оценить на test.

**Выход:** Test Design — план тренировки, тестирования, оценки. Решить: как делить данные на train/test/validation. Число итераций, fold'ов.

#### 4.3 Build Model
**Задача:** Запустить инструмент, создать модель(и).

**Выходы:** Parameter Settings (параметры + обоснование выбора), Models (сами модели), Model Description (интерпретация, возможные недостатки).

#### 4.4 Assess Model
**Задача:** Оценить модели по DM-критериям и test design. Ранжировать результаты. Оценить достоверность, плюсы/минусы.

**Выходы:**
- Model Assessment — качество (accuracy), ранжирование, интерпретация в бизнес-терминах (насколько возможно), проверка здравого смысла, потенциал деплоя
- Revised Parameter Settings — итерировать до лучшей модели

**Активности:** Lift/Gain tables, тестирование (Train&Test, Cross-validation, bootstrapping), правдоподобность модели, новизна и полезность найденного, анализ правил (если есть) — логичны ли? осуществимы ли?

### Фаза 5: Evaluation (стр. 32–35)

Ключевая формула: **RESULTS = MODELS + FINDINGS**

Models — напрямую связаны с бизнес-вопросами. Findings — всё остальное важное (не обязательно связанное с исходными целями): новые вопросы, побочные эффекты, проблемы качества данных, обнаруженные в ходе проекта.

#### 5.1 Evaluate Results
**Задача:** Оценить степень достижения бизнес-целей. Не то же самое, что оценка модели в фазе 4 (техническая). Здесь: бизнес-оценка. Есть ли бизнес-причина, по которой модель неудовлетворительна?

**Выходы:** Assessment of Data Mining Results vs Business Success Criteria (финальное заявление: достигнуты ли цели), Approved Models.

#### 5.2 Review Process
**Задача:** Ретроспектива. Всё ли учтено? Качество процесса — QA review. Не упущен ли важный фактор или задача?

**Выход:** Review of Process — пропущенные активности, вводящие в заблуждение шаги, альтернативные пути.

#### 5.3 Determine Next Steps
**Задача:** Решение: деплоить, итерировать, или начать новый проект. Анализ оставшихся ресурсов и бюджета.

**Выходы:** List of Possible Actions (аргументы за/против каждого), Decision (решение + обоснование).

### Фаза 6: Deployment (стр. 36–40)

Создание модели — НЕ конец проекта. Даже если цель = увеличение знаний, результаты нужно организовать для клиента.

#### 6.1 Plan Deployment
**Задача:** Стратегия деплоя. Оценить альтернативы, определить возможные проблемы.

**Выход:** Deployment Plan — шаги и как их выполнить.

#### 6.2 Plan Monitoring and Maintenance
**Задача:** Критически важно если результат DM входит в ежедневный бизнес-процесс. Без плана мониторинга = длительное некорректное использование.

**Выход:** Monitoring and Maintenance Plan. Когда модель НЕ должна использоваться? (валидность, порог точности, новые данные, изменения в домене). Что делать? (обновить, новый проект). Изменятся ли бизнес-цели? Документировать исходную проблему!

#### 6.3 Produce Final Report
**Выходы:**
- **Final Report** — все потоки вместе: результаты, процесс, затраты, отклонения от плана, план имплементации, рекомендации. Содержание зависит от аудитории
- **Final Presentation** — подмножество отчёта, структурированное иначе. Определить аудиторию, учесть получали ли они отчёт

#### 6.4 Review Project
**Задача:** Что прошло хорошо, что плохо, что улучшить.

**Выход:** Experience Documentation — ловушки, вводящие в заблуждение подходы, советы по выбору техник. Включает отчёты участников. Абстрагировать от деталей для полезности в будущих проектах. Интервью всех значимых участников. Если конечные пользователи работают с результатом — интервью и их.

## III. User Guide — ключевые дополнения (стр. 41–78)

User Guide дублирует Reference Model, но добавляет Activities (конкретные шаги) и подсказки (Good Idea, Beware, Remember).

### Ключевые дополнения User Guide, не описанные в Reference Model:

**Business Understanding:**
- Распределение усилий по фазам: Data Preparation 50-70%, Data Understanding 20-30%, Modeling/Evaluation/BU по 10-20%, Deployment 5-10%
- Перед Assess Situation рассмотреть предыдущий опыт (внутренний или внешние решения)
- Определить целевую группу для результатов проекта (отчёт для top-менеджмента vs running system для конечных пользователей)
- Project Plan — динамический документ, пересматривается после каждой фазы

**Data Understanding:**
- Качество данных оценивать не только для отдельных источников, но и для объединённых данных (merged data может иметь проблемы, которых нет в отдельных источниках)
- Учитывать сколько истории нужно (даже если 18 месяцев доступно — может хватить 12)
- Знания могут быть в нецифровой форме (люди, печатные тексты)

**Data Preparation:**
- Перед созданием derived attributes определить: облегчают ли они моделирование? «Доход на человека» может быть лучше «дохода на домохозяйство»
- Не создавать derived attributes просто для уменьшения количества входных
- Специальные значения (99 = unknown, 00 = truncated) — источник странных результатов

**Modeling:**
- Не все техники доступны для каждой задачи. Вселенная техник сужается: Universe → Appropriate for Problem → Available in Tool → Meeting Political Requirements
- Lift Tables и Gain Tables для оценки

**Evaluation:**
- RESULTS = MODELS + FINDINGS
- Findings могут быть важнее моделей (новые вопросы, проблемы данных)

## V. Appendix: Типы задач data mining (стр. 82–91)

Проект обычно включает последовательность разных типов задач.

### Data Description and Summarisation
Описание характеристик данных. Может быть самостоятельной целью (отчёт по обороту торговых точек). Но чаще — подзадача на ранних этапах (EDA). Делать ПЕРЕД любым другим типом задач. Простые инструменты: reporting, OLAP, EIS, статистические пакеты.

### Segmentation (= Clustering)
Разделение на подгруппы с общими характеристиками. Может быть целью (кого включить в рассылку?) или шагом к другим задачам (зависимости в сегментах легче найти). Техники: clustering, neural nets, визуализация. Не путать с classification (segmentation создаёт классы, classification предсказывает известные).

### Concept Descriptions
Понятное описание концепций/классов. Цель — инсайты, не точность предсказания. Пример: что характеризует лояльных vs нелояльных клиентов? Не обязательно полное — достаточно описать важные части. Техники: rule induction, conceptual clustering.

### Classification
Набор объектов с атрибутами, принадлежащих разным классам (метка класса — дискретная, известна). Цель: построить модель, правильно присваивающую класс новым объектам. Одна из важнейших задач. Многие задачи трансформируются в classification. Техники: discriminant analysis, rule induction, decision trees, neural nets, kNN, case-based reasoning, genetic algorithms.

### Prediction (= Regression / Forecasting)
Как classification, но таргет — непрерывный. Найти числовое значение для новых объектов. Для time series = forecasting. Техники: regression analysis, regression trees, neural nets, kNN, Box-Jenkins, genetic algorithms.

### Dependency Analysis (= Association)
Модель значимых зависимостей между элементами данных. Используется для понимания. Associations = частный случай (часто встречающиеся вместе элементы, напр. shopping basket: «в 30% покупок пиво + орехи»). Алгоритмы быстрые, генерируют много ассоциаций — выбор интересных = challenge. Техники: correlation, regression, association rules, Bayesian networks, ILP, visualization.

# ЧАСТЬ 2: Нетбай и др. (2020) — «Прогнозное управление теплоснабжением» (10 стр.)

## Контекст и мотивация

### Проблема ручного управления
Сейчас на котельных температуру теплоносителя на выходе задаёт оператор дежурной смены вручную каждые 2 часа, ориентируясь на текущую температуру воздуха (термометр). Это реактивное управление — реакция на ТЕКУЩИЕ условия, без учёта прогноза.

### Зачем автоматизация
Автоматическое поддержание температуры по «Температурному графику» обеспечивает рациональный режим сгорания с максимальным КПД. Экономия — 12-15% газа в год для рассматриваемой котельной.

### Зачем прогнозное управление (следующий шаг после автоматизации)
Текущая автоматика поддерживает заданную температуру, но НЕ учитывает:
- Прогноз погоды на несколько часов вперёд
- Инерционность теплосети (запаздывание между изменением температуры на котельной и в домах)

Из-за этого организация вынуждена поддерживать **заведомо высокую** температуру на выходе из котельной → температура в домах **значительно выше** нормативной → **перетоп** → перерасход топлива.

По расчётам «СОФТ-М»: снижение температуры в домах до уровня «не ниже требуемой на 3%» даст **дополнительную экономию 5-10% в год** (поверх 12-15% от автоматизации).

### Итого ожидаемая экономия: 5-15%

## Описание системы теплоснабжения

### Топология
Теплосеть — **древовидная структура**. Корень — котельная. Ветви — тепловые коллекторы (ТК). Листья — многоквартирные дома (МКД). Элементы соединены трубами.

### Физика потерь
При движении теплоносителя по трубам его внутренняя энергия частично рассеивается в окружающую среду. Поэтому:
- Температура на выходе из котельной > температура на входе в дома
- Разница **непостоянна** и зависит от температуры теплоносителя, температуры воздуха **нелинейно**

### Инерционность теплосети
Инерционность = время запаздывания реакции в домах на изменение температуры на котельной. Зависит от:
- Топологии сети (расстояние, разветвлённость)
- Скорости движения теплоносителя

Инерционность заранее неизвестна и нетривиальна. Важна для выбора периода прогнозного управления.

## Математическая постановка задачи

### Входные данные
- Tк — температура воды на выходе из котла
- Тi (i = 1…m) — температура теплоносителя на входе в i-й МКД
- m — количество потребителей
- Тв — текущая температура воздуха
- ΔТв — прогнозное изменение температуры воздуха за время Δt

### Что найти
Оптимальное изменение ΔТк за время Δt, чтобы:
1. **Ограничение снизу** (жёсткое): Тi(t+Δt) ≥ Т* — температура на входе в каждый МКД НЕ ниже нормативной
2. **Минимизация перетопа** (мягкое): сумма (Тi(t+Δt) – Т*) → min — совокупное отклонение вверх минимально

Т* — нормативная температура, зависящая от температуры воздуха (из «Температурного графика»).

### Сложности
1. Зависимость Тк → Тi — **нелинейная**, зависит от топологии, скорости, состояния сети, теплопотерь
2. **Инерционность** — время реакции неизвестно, зависит от топологии и скорости

### Два подхода к решению
1. **Модельный** — построить математическую модель теплосети (сложно, для каждой сети отдельно)
2. **Безмодельный (model-free)** — определить зависимости из статистических данных через обучение нейросети. Обладает необходимой общностью и более эффективен. **Этот подход выбран.**

## Нейросетевое моделирование

### Архитектуры
Рассмотрены:
- **Многослойный персептрон (MLP)** — опробованы 1, 2 и 3 скрытых слоя
- **LSTM** — рекуррентная сеть глубокого обучения

Лучшие результаты: **MLP с 3 скрытыми слоями**, 224 нейрона.

### Вход/выход
- **Вход:** m значений температур на входе в дома (m = число потребителей)
- **Выход:** одно значение — температура на выходе из котельной

### Защита от переобучения
- Метод **dropout** с вероятностью **0.2** (каждый нейрон «выключается» с вероятностью 20% на каждой итерации обучения)

### Обучение
- Данные: АСУ «Aurora. Тепловой баланс в ЖКХ», котельная г. Лысьва Пермского края, сезон 2018/19
- Данные: температура теплоносителя на выходе котельной + на входе в дома + температура воздуха
- Частота: каждые 3 минуты (температура), каждые 10 минут (воздух)
- Функция потерь: среднее квадратичное отклонение (MSE)
- Оптимизатор: **Adam**
- Итерации: 200 эпох

### Результаты обучения

| Показатель | Обучающая | Тестовая |
|---|---|---|
| Среднее квадратичное отклонение | 0.87% | 1.3% |
| Средняя относительная ошибка | 1.3% | 2.1% |
| Средняя ошибка (°C) | — | 0.35 |
| Максимальная ошибка (°C) | — | 3.43 |

Средняя ошибка 0.35°C — нейросеть точно определяет температуру.
Максимальная ошибка 3.43°C — при резких изменениях.

## Прогнозное управление (демонстрация)

### Параметры
- Период: февраль 2019 (самый холодный месяц)
- Период управления: **3 часа** (учитывая инерционность сети и доступность прогноза)
- Алгоритм: каждые 3 часа по прогнозу температуры воздуха → нормативное значение в домах → через нейросеть → оптимальная температура котла

### Результаты сравнения с ручным управлением

Ключевой пример: 2-5 февраля 2019 — резкое похолодание (до -22.88°С).

Нейросеть предлагает **повысить температуру на ~8°C** по сравнению с оператором. Это предотвратило бы снижение температуры ниже нормативной в некоторых домах.

### Данные по отклонениям (из таблицы 2)

Средние отклонения предсказанной температуры в домах от реальной: от -0.50°C до +0.84°C. Это высокая точность.

### Ключевые наблюдения
1. Нейросетевое управление **более плавное** по сравнению с ручным (оператор реагирует скачками каждые 3 часа)
2. Нейросеть **быстрее реагирует** на изменения погоды (учитывает прогноз, а не текущее значение)
3. При **резком похолодании** нейросеть повышает температуру ЗАРАНЕЕ (оператор запаздывает)
4. При **потеплении** нейросеть снижает температуру быстрее (экономия vs перетоп)
5. Колебания температуры воздуха в рассматриваемый период — до 20°C мороза

## Заключение авторов

1. Сформулирована актуальная задача безмодельного прогнозного управления
2. Обоснован нейросетевой метод для нелинейной задачи
3. Обучен MLP с 3 скрытыми слоями на реальных данных — адекватные результаты
4. Демонстрация подтверждает работоспособность подхода
