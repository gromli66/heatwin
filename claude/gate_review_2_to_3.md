# Точка принятия решения: Gate Review между фазой 2 и фазой 3

## Что это и зачем

После завершения EDA (фаза 2) и перед началом feature engineering (фаза 3) нужно остановиться и ответить на вопрос: **то, что мы узнали о данных, подтверждает наш план или ломает его?**

Это не формальность. По данным CRISP-DM: «бизнес-цели могут потребовать корректировки на основе понимания, полученного на фазах data understanding и data preparation». По результатам EDA возможны три исхода:

1. **Зелёный свет** — план подтверждён, двигаемся в фазу 3
2. **Жёлтый свет** — план в целом верен, но нужны корректировки (scope, метрики, допущения)
3. **Красный свет** — критические проблемы, нужно вернуться в фазу 1 и пересмотреть Project Brief

**Источник:** CRISP-DM (итеративность между фазами) + Stage-Gate (Robert Cooper) + практики review в Agile DS.

## Шаг 2: Ревизия контракта метрик

По результатам EDA метрики из Project Brief (раздел 3.3) могут потребовать уточнения.

### Чеклист

- [ ] Primary metric (energy_per_HDD) рассчитана на реальных данных — получено конкретное baseline значение
- [ ] Guardrail (T_return > T_min) проверен — какой % данных нарушает порог сейчас? Это норма или проблема?
- [ ] Secondary metrics рассчитаны — есть ли baseline для числа перетопов, аварийных корректировок?
- [ ] MDE (minimal detectable effect = 5%) реалистичен? Сколько это в абсолютных единицах на реальных данных?
- [ ] Если baseline ≠ ожиданиям — нужна ли корректировка KPI?

### Возможные корректировки

| Ситуация после EDA | Действие |
|---|---|
| Baseline energy_per_HDD уже оптимален (мало перетопа) | Снизить MDE или пересмотреть primary metric |
| Guardrail нарушается в 20% часов уже сейчас | Это не модель ломает — это текущий режим. Зафиксировать как baseline |
| Energy имеет 30% нулей (отключения) | Добавить бинарный классификатор «вкл/выкл» перед регрессией |
| Мультиколлинеарность T_supply ↔ T_return r > 0.95 | Убрать T_supply из features или использовать ΔT вместо обоих |
| Суточная периодичность подтверждена (ACF lag-24) | Включить T_return_lag_24h в обязательные features |
| Выходные значимо отличаются (Mann-Whitney p < 0.01) | Включить is_weekend в features |

## Шаг 3: Ревизия scope и подхода к моделированию

EDA может показать, что исходный план моделирования нужно скорректировать.

### Чеклист

- [ ] Таргет T_return_primary(t+6h) формируем через shift(-6) — проверено, что данные позволяют (достаточно записей, нет разрыва на границах сезонов)
- [ ] Определено: одна модель на все подстанции или отдельная на каждую? (EDA показал различия или нет?)
- [ ] Определено: какие подстанции включаем в MVP (достаточно данных по всем или начинаем с L4?)
- [ ] Определено: какой период берём для обучения (все сезоны или только после change-point?)
- [ ] Определено: нужен ли бинарный классификатор «система вкл/выкл» перед регрессией T_return?
- [ ] Лог гипотез из EDA (задача 2.3) пересмотрен — приоритезированы features для первой итерации
- [ ] Out of scope (Project Brief раздел 7.2) — нужно ли что-то добавить или убрать после EDA?

### Возможные изменения подхода

| Находка EDA | Изменение подхода |
|---|---|
| Подстанции сильно различаются | Отдельная модель на каждую (или substation как feature) |
| Подстанции похожи | Одна общая модель (больше данных для обучения) |
| Есть change-point в середине архива | Train только на данных после change-point |
| Нет change-point | Используем весь архив |
| T_return слабо зависит от T_outdoor напрямую | Нужны промежуточные features (ΔT, HDD, лаги) — усложнить feature engineering |
| T_return хорошо предсказывается T_outdoor + lag-1 | Простая модель может быть достаточной — не переусложнять |
| Данных < 1 сезона по некоторым подстанциям | Исключить из MVP, начать с подстанций с полным архивом |

## Шаг 6: Формальное решение

### Варианты

| Решение | Когда | Что делаем дальше |
|---|---|---|
| **🟢 GO** | Все допущения подтверждены или некритичны. Baseline получен. Scope не меняется. | Переходим в фазу 3. Project Brief обновлён (v1.1) с реальными baseline. |
| **🟡 GO с корректировками** | Часть допущений опровергнута, но решаемо. Scope сужается. Метрики уточняются. | Обновляем Project Brief (v1.1), документируем изменения, переходим в фазу 3 с изменённым планом. |
| **🔴 STOP** | Данных недостаточно. Таргет непрогнозируем. Guardrail непроверяем. | Возвращаемся в фазу 1. Пересматриваем бизнес-задачу, ищем дополнительные данные, меняем подход. |

## Артефакт этого шага

**Gate Review Report** — 1-2 страницы:
1. Таблица допущений с вердиктами (шаг 1)
2. Baseline метрик в реальных числах (шаг 2)
3. Корректировки подхода если есть (шаг 3)
4. Обновлённые риски (шаг 4)
5. Решение: GO / GO с корр. / STOP (шаг 6)

Этот документ — мост между EDA Notebook (техника) и обновлённым Project Brief (бизнес). Он отвечает на вопрос: **«мы проверили — данные подтверждают наш план или нет?»**
