## Задача 2.2: Описание данных (Describe Data)

### Что делаем

- Описательная статистика по каждой переменной: mean, median, std, min, max, квартили

Понять «поверхностные свойства» данных до глубокого анализа. Это как осмотр пациента перед анализами. Часто уже на этом этапе видны проблемы: T_outdoor = 999°С (ошибка датчика), energy = -50 (невозможное значение), std = 0 (замёрзший датчик).

## Задача 2.3: Исследование данных (Explore Data)

### Что делаем

#### 2.3.1 Визуализации распределений
- Гистограммы / KDE для каждой переменной
- ECDF (эмпирическая функция распределения)
- Box-plot / Violin plot по подстанциям и сезонам
- QQ-plot для проверки нормальности

#### 2.3.2 Временные ряды
- Графики временных рядов T_supply, T_return, energy, T_outdoor
- Декомпозиция: тренд + сезонность + остаток
- ACF (автокорреляционная функция) — до 168 лагов (неделя)
- PACF (частная ACF) — для определения порядка лагов

#### 2.3.3 Корреляционный анализ
- Матрица корреляций Пирсона (все числовые переменные)
- Корреляция Спирмена (если есть нелинейные зависимости)
- Scatter plots ключевых пар: T_supply vs T_outdoor (отопительная кривая), energy vs T_outdoor, T_supply vs T_return

#### 2.3.4 Суточные и недельные профили
- Средние по часам суток (daily profile)
- Сравнение будни vs выходные
- Средние по месяцам (seasonal profile)

#### 2.3.5 Подбор распределений
- Тест Шапиро-Уилка (нормальность)
- KS-тест (согласие с распределением)
- Подгонка MoM и MLE для Gamma (energy_kWh), Normal (T_outdoor)
- QQ-plot для подобранных распределений

#### 2.3.6 Проверка стационарности
- ADF-тест (Augmented Dickey-Fuller)
- KPSS-тест
- Визуальная проверка: rolling mean и rolling std

#### 2.3.7 Измерение инерционности теплосети (из Нетбая)
- Cross-correlation между t_sup_prim(t) и t_ret_sec(t+lag) для lag = 0..24h
- Определить lag с максимальной корреляцией = инерционность данной подстанции
- Сравнить между подстанциями (L4/L17 крупнее → инерционность больше?)
- **Результат определяет горизонт прогноза:** если инерционность ~3ч (как у Нетбая для Лысьвы), горизонт 6ч обоснован. Если 1ч — можно сократить
- Нетбай (2020): для теплосети г. Лысьва период управления = 3 часа на основе инерционности
- Визуализация: heatmap cross-correlation по лагам × подстанциям

### Для чего
Это ядро EDA. Цели: (а) подтвердить или опровергнуть допущения из Project Brief (раздел 6.2), (б) найти закономерности для feature engineering (фаза 3), (в) обнаружить аномалии и change-points, (г) проверить мультиколлинеарность (раздел 2.3.3 предыдущего обсуждения).

### Блоки роадмапы
- **3.1**: визуализация — histogram/KDE, ECDF, box/violin, QQ-plot, scatter/hexbin
- **3.1**: диагностика — heavy-tail, zero-inflation, выбросы, зависимость
- **4.1**: распределения — Normal, Gamma, LogNormal; LLN/CLT; дельта-метод
- **5.1**: подстановка и эмпирическая CDF, метод моментов, выборочные квантили
- **5.2**: MLE — условия регулярности, инвариантность, асимптотическая нормальность
- **11.1**: стационарность — ADF/KPSS; автокорреляция — Ljung-Box
- **12.5**: согласие — KS, Anderson-Darling, Shapiro-Wilk
- **12.8**: корреляция — Pearson, Spearman
- **12.10**: time series — ADF, KPSS, Ljung-Box

### Артефакт
- EDA Notebook (Jupyter) с визуализациями и выводами
- Data Exploration Report: ключевые находки, гипотезы для feature engineering
- **Лог гипотез:** таблица «EDA-наблюдение → статистический вывод → действие для моделирования» (пример: «ACF пик на лаге 24 → суточная периодичность, p < 0.001 по Ljung-Box → включаем T_return_lag_24h в features»)

### Правила оформления визуализаций
- **«So what?»:** под каждым графиком — 1-2 предложения вывода. Что это означает для моделирования? Что для бизнеса?
- **Статистический тест к каждому визуальному claim:** «распределение нормальное» → Shapiro-Wilk p = X. «Будни отличаются от выходных» → Mann-Whitney U p = X. Без p-value визуальное утверждение — мнение, не факт.
- **Аннотации на графиках:** стрелки, выноски, подписи с бизнес-контекстом. Не просто линия T_return, а стрелка «здесь перетоп: T_return выше нормы на 3°С в течение 8 часов».
- **Перевод в бизнес-контекст:** не «корреляция = -0.83», а «температура подачи хорошо следует за погодой, но в 15-25% случаев перетоп — потенциал экономии».

## Задача 2.4: Проверка качества данных (Verify Data Quality)

### Что делаем
- Подсчёт пропусков по каждой переменной и подстанции
- Поиск дубликатов (одинаковый timestamp + substation)
- Поиск выбросов: IQR-метод, z-score, визуальный (box-plot)
- Проверка физической корректности: T_return < T_supply? energy ≥ 0? T_outdoor в [-40, +40]?
- Проверка временной регулярности: одинаковый ли шаг (1 час)? Нет ли пропущенных часов?
- Поиск «замёрзших» датчиков: std = 0 на окне 24h
- Анализ нулевых значений energy (отключения vs ошибки)
- Change-point detection: CUSUM или визуальный — есть ли структурный сдвиг в данных
- **Pandera-схема для raw data** (из фазы 0): декларативная валидация — описать ожидаемые типы, диапазоны, ограничения. Запускается автоматически через `make validate`

### Для чего
Garbage in — garbage out. Качество данных напрямую определяет качество модели. Этот этап решает: можно ли работать с данными «как есть», или нужна серьёзная предобработка (фаза 3). Также проверяет допущение из Project Brief «данные XAI4HEAT прошли предобработку и не содержат пропусков» — так ли это?

### Блоки роадмапы
- **3.1**: качество данных — пропуски, дубли, late events
- **3.1**: диагностика — выбросы и leverage
- **12.10** (частично): change-point — CUSUM

### Артефакт

## Задача 2.5: Упаковка результатов (Packaging — не из CRISP-DM)

**Источник:** практики коммуникации DS-результатов, executive reporting, Storytelling with Data (Knaflic). Не входит в оригинальный CRISP-DM, но критично для «продажности» EDA.

### Зачем
EDA имеет двух потребителей. Технический рецензент проверяет строгость и воспроизводимость. Нетехнический стейкхолдер (директор, главный инженер) хочет понять: что значат эти данные для его котельной? Один Jupyter Notebook не может обслужить обоих. Нужны два выхода.

### Выход 1: EDA Notebook (для технического рецензента)

Jupyter Notebook с кодом, но оформленный как презентабельный документ:

#### Что добавить к стандартному notebook
- **Автопрофиль в начале:** ydata-profiling HTML как первая ячейка — рецензент за 30 секунд видит общую картину
- **Лог гипотез после каждого блока:** таблица «наблюдение → тест (p-value) → действие для моделирования»
- **p-value рядом с каждым визуальным утверждением:** «выглядит нормальным» — не доказательство. Shapiro-Wilk p = 0.03 → отвергаем — доказательство
- **Таблица проверки допущений:** формальная сверка с разделом 6.2 Project Brief — до/после с комментарием

| Допущение из Project Brief | Статус до EDA | Статус после EDA | Комментарий |

| Часового шага достаточно | Не проверено | Требует проверки | ACF показывает значимые 15-мин лаги |
| Подстанции независимы | Не проверено | Частично опровергнуто | Кросс-корреляция L4-L8 = 0.72 |

- **Воспроизводимость:** requirements.txt с версиями библиотек, random seed фиксирован, хэш датасета (или Mendeley DOI), путь к данным параметризован через переменные

### Выход 2: EDA Summary Report (для нетехнического стейкхолдера)

Отдельный документ на 3-5 страниц (PDF или DOCX), без единой строки кода:

#### Структура
1. **Executive Summary (1 страница):** «Мы изучили данные за 5 отопительных сезонов с 5 подстанций. Данные пригодны для прогнозирования. Обнаружены 3 ключевые закономерности (см. ниже). Ожидаемый потенциал экономии: X-Y%. Главные риски данных: Z.»

2. **Ключевые находки (1-2 страницы, 5-7 аннотированных визуализаций):**
   - Каждый график подписан на понятном языке, без терминов (не «ACF с лагом 24», а «потребление тепла повторяется каждые сутки — система предсказуема»)
   - Стрелки и выноски показывают: «вот здесь перетоп», «вот здесь экономия возможна»
   - Рядом с каждой находкой — перевод в рубли через экономическую модель из Project Brief (раздел 3.4): «В 12% часов T_supply выше оптимального на ≥2°С. При расходе X м³/ч это ≈ Y тыс. руб/сезон перерасхода»

3. **Сравнение с бенчмарком (0.5 страницы):**
   - Наши данные типичны или аномальны? Сравнение с литературой
   - По Нетбаю: типичная экономия 5-15%. Наш EDA показывает потенциал перетопа Y% — в пределах / выше / ниже ожидаемого
   - XAI4HEAT проект заявляет цель 10% снижения — наши данные позволяют / не позволяют это ожидать

4. **Риски и ограничения данных (0.5 страницы, на понятном языке):**
   - Не «30% zero-inflation в energy_kWh», а «система отключается примерно 30% времени — в эти периоды прогноз невозможен, но это штатный режим»
   - Не «ADF p = 0.02», а «данные достаточно стабильны для построения надёжной модели»
   - Не «мультиколлинеарность T_supply и T_return r=0.97», а «температуры подачи и обратки движутся почти синхронно — для модели достаточно одной из них»

5. **Рекомендации и следующие шаги (0.5 страницы):**
   - Конкретные решения: «Рекомендуем начать с подстанции L4 (больше всего данных). Использовать лаги 1-24h и календарные признаки. Guardrail T_return = 42°С подтверждён. Следующий шаг — feature engineering и baseline-модель.»

## Задача 2.6: Создание EDA-дашборда (Dashboard — не из CRISP-DM)

**Источник:** практика DS-портфолио и data storytelling. Не входит в CRISP-DM, но критично для пет-проекта: дашборд = живое портфолио, которое можно показать на собеседовании.

### Когда какой дашборд

| Фаза | Тип дашборда | Цель | Аудитория |
|---|---|---|---|
| **Фаза 2 (сейчас)** | EDA-дашборд | Интерактивный отчёт: фильтры по подстанциям/сезонам, распределения, корреляции, временные ряды | DS-рецензент + клиент |
| Фаза 5 (Evaluation) | Дашборд результатов модели | Backtesting: прогноз vs факт, метрики, what-if | Технический комитет |
| Фаза 6 (Deployment) | Продуктовый дашборд оператора | Прогноз T_return, рекомендация уставки, guardrail-индикатор | Оператор котельной |

В фазе 2 делаем **только EDA-дашборд**. Остальные — позже.

### Что должно быть на EDA-дашборде

#### Страница 1: Обзор данных (Overview)
- Карточки-метрики: количество записей, период, число подстанций, % пропусков
- Selector: подстанция, сезон, переменная
- Временной ряд выбранной переменной с фильтрами
- Описательная статистика выбранного среза (таблица)

#### Страница 2: Распределения и качество
- Гистограмма / KDE выбранной переменной (с фильтром по подстанции)
- Box-plot по подстанциям (сравнение масштабов)
- QQ-plot для проверки нормальности
- Индикатор пропусков / выбросов / zero-inflation

#### Страница 3: Корреляции и зависимости
- Интерактивная корреляционная матрица (hover = scatter)
- Отопительная кривая T_supply vs T_outdoor (scatter + regression line + R²)
- Scatter plot: energy vs T_outdoor (с цветом по подстанции)

#### Страница 4: Временные паттерны
- Суточный профиль (средние по часам, будни/выходные переключатель)
- Сезонный профиль (по месяцам)
- ACF-график (с слайдером числа лагов)

#### Страница 5: Ключевые находки (Executive)
- 3-5 аннотированных визуализаций из задачи 2.5 (Summary Report)
- Перевод в рубли (экономическая оценка перетопа)
- Сравнение с бенчмарком (Нетбай 5-15%, XAI4HEAT 10%)
- Рекомендации и следующие шаги

### Где делать: выбор технологии

#### Результаты ресёрча рынка (2024-2025)

**Для DS-пет-проекта (наша ситуация):**

| Инструмент | Рынок РФ | Рынок ЕС | Сложность | Для кого | Рекомендация |
|---|---|---|---|---|---|
| **Streamlit** | Активно растёт, упоминается в вакансиях DS | Лидер по загрузкам (972K/мес) | Низкая | DS без фронтенд-опыта | **★ Рекомендован для нашего проекта** |
| **Plotly Dash** | Востребован в enterprise | 2-е место (902K/мес) | Средняя (нужен HTML) | DS с базовым пониманием веба | Хорош, но сложнее Streamlit |
| **Grafana** | Популярен в DevOps/мониторинге | Лидер для real-time мониторинга | Средняя | Инженеры, IoT, SCADA | Для фазы 6 (продуктовый дашборд), не для EDA |
| **Apache Superset** | Растёт в РФ, open-source BI | Популярен в enterprise | Средняя-высокая | Аналитики, BI | Для BI-аналитиков, избыточен для DS-пет-проекта |
| **Power BI** | Доминирует в корпоративном сегменте РФ | Лидер enterprise BI | Низкая (GUI) | Бизнес-аналитики | Не Python, не для DS-портфолио |
| **Metabase** | Растёт, open-source | Популярен в стартапах | Низкая (no-code) | Нетехнические пользователи | Не для DS, нет Python-интеграции |
| **Panel (HoloViz)** | Мало известен | Набирает популярность в PyData | Средняя | DS в Jupyter | Перспективный, но мало вакансий |

**Обоснование выбора Streamlit:**
1. Минимальный порог входа — Python-скрипт превращается в веб-приложение за 10 строк кода
2. Востребован на рынке — упоминается в вакансиях DS в РФ и ЕС, приобретён Snowflake
3. Хорошая интеграция с pandas, plotly, matplotlib, seaborn — всё, что уже используем в EDA
4. Бесплатный деплой на Streamlit Cloud — можно дать ссылку рецензенту/клиенту
5. Multipage apps — наши 5 страниц реализуются нативно
6. Не учим лишнего — навык переносится и на другие Python-проекты

**Когда НЕ Streamlit:**
- Фаза 6 (продуктовый дашборд оператора) — рассмотреть Grafana (мониторинг real-time) или Plotly Dash (enterprise-масштаб)
- Если клиент — крупная корпорация с Power BI инфраструктурой — делать в Power BI
- Если нужен BI для нетехнических пользователей — Metabase или Superset
