## Задача 3.2: Очистка данных (Clean Data)

### Что делаем

#### 3.2.1 Пропуски
- Стратегия зависит от типа пропуска (из Data Quality Report):
  - MCAR (случайные): линейная интерполяция для температур, forward-fill для категорий
  - MAR (зависимые от наблюдаемых): интерполяция с учётом T_outdoor (если T_return пропущен при известном T_outdoor)
  - MNAR (зависимые от ненаблюдаемых): флаг is_imputed, не импутировать таргет
- Таргет T_return НЕ ИМПУТИРУЕТСЯ — записи с пропущенным таргетом исключаются

#### 3.2.2 Выбросы
- IQR-метод (из EDA) → решение для каждой переменной:
  - T_supply, T_return: clipping к физически допустимому диапазону (из раздела 2.4 Project Brief)
  - energy: нули — не выбросы (отключения), но экстремально высокие → проверить, clipping если > 3σ
  - T_outdoor: проверить по метеоданным, обычно корректны
- Записывается: сколько выбросов, по каким переменным, какое решение

#### 3.2.3 Дубликаты и временная регулярность
- Удаление полных дубликатов (timestamp + substation)
- Заполнение пропущенных часов (если шаг нерегулярный) — reindex + interpolate
- Проверка монотонности timestamp (нет ли «прыжков назад»)

#### 3.2.4 Физическая валидация
- T_return < T_supply (всегда) — если нарушено → исключить или пометить
- energy ≥ 0 (всегда) — если отрицательно → исключить
- T_outdoor в [-40, +40] — если вне → ошибка датчика, исключить

### Для чего
Garbage in — garbage out. Но также: overcleaning — потеря информации. Баланс: убрать явные ошибки, не убрать редкие но реальные режимы (экстремальные морозы = реальность, не выброс).

### Блоки роадмапы
- **3.1**: качество данных — пропуски, дубли, выбросы
- **3.1**: диагностика — leverage points

### Артефакт
- Data Cleaning Report: что очищено, сколько, каким методом, сколько записей осталось

### Чеклист готовности
- [ ] Пропуски: стратегия выбрана для каждой переменной и задокументирована
- [ ] Таргет: записи с пропущенным T_return исключены (НЕ импутированы)
- [ ] Выбросы: для каждой переменной — решение (clipping / исключение / оставить)
- [ ] Дубликаты удалены, количество записано
- [ ] Временная регулярность: шаг ровно 1 час, пропущенные часы заполнены

## Задача 3.3: Конструирование признаков (Construct Data — Feature Engineering)

### Что делаем

Это ядро фазы 3. Каждая группа features привязана к типу памяти из концепции HeatWin и к находкам EDA (лог гипотез).

#### 3.3.1 Конструирование таргета
- `target = df.groupby('substation')['T_return_primary'].shift(-h)` где h = горизонт (6 часов)
- Последние h строк каждого сезона/подстанции → NaN → исключить
- Проверка: нет ли data leakage (таргет не входит в features текущего момента)

#### 3.3.2 Группа 1: Физическая инерция (лаги и агрегаты)
**Обоснование из EDA:** ACF показал сильные лаги на 1h, 6h, 12h, 24h

- Лаги T_return: lag_1h, lag_3h, lag_6h, lag_12h, lag_24h
- Лаги T_supply: lag_1h, lag_3h, lag_6h, lag_12h, lag_24h
- Лаги T_outdoor: lag_1h, lag_3h, lag_6h, lag_12h, lag_24h
- Лаги energy: lag_1h, lag_6h, lag_24h
- Скользящие средние (SMA): T_return SMA_3h, SMA_6h, SMA_12h, SMA_24h
- Скользящие std: T_return std_3h, std_6h, std_12h, std_24h (волатильность)
- EMA (экспоненциальное среднее): T_return EMA_6h, EMA_24h
- Скорости изменения: dT_return/dt (1h), dT_supply/dt (1h), dT_outdoor/dt (1h, 3h)

#### 3.3.3 Группа 2: Поведенческая периодичность (календарные)
**Обоснование из EDA:** суточный двугорбый профиль, различие будни/выходные

- Час суток: sin/cos кодирование — hour_sin = sin(2π × hour/24), hour_cos = cos(2π × hour/24)
- День недели: sin/cos кодирование — weekday_sin, weekday_cos
- Бинарные: is_weekend, is_night (22-06)
- Месяц: month (или sin/cos если нужна цикличность)
- Периодические лаги: T_return_24h_ago (вчера в это же время), T_return_168h_ago (неделю назад)
- Периодические лаги energy: energy_24h_ago, energy_168h_ago

#### 3.3.4 Группа 3: Климатическая память
**Обоснование из EDA:** отопительная кривая R² < 1.0 — остаток объясняется накопленным холодом

- HDD (градусо-сутки): HDD_hourly = max(0, 18 - T_outdoor), HDD_1d, HDD_3d, HDD_7d (rolling sum)
- T_outdoor_min за 1d, 3d, 7d (минимум за окно — индикатор экстремальных холодов)
- T_outdoor_mean за 1d, 3d, 7d (средняя за окно)
- Разность текущей T_outdoor и средней за 24h (резкое похолодание/потепление)

#### 3.3.5 Группа 4: Производные признаки
**Обоснование из EDA:** мультиколлинеарность T_supply ↔ T_return

- ΔT_primary = T_supply - T_return (перепад — физически значимее чем абсолютные значения)
- ΔT_secondary = T_supply_secondary - T_return_secondary (если используем вторичный контур)
- heat_exchanger_loss = T_supply_primary - T_supply_secondary (потери на теплообменнике)
- energy_per_m2 = energy_kWh / heating_area_m2 (нормированное потребление)
- supply_outdoor_diff = T_supply - T_outdoor (отклонение от равновесия)

#### 3.3.6 Кодирование подстанции (если общая модель)
- One-hot encoding: substation_L4, substation_L8, ...
- Или: heating_area_m2 как числовой признак (несёт ту же информацию но компактнее)

### Для чего
Feature engineering — это перевод domain knowledge (из интервью с оператором, из литературы, из EDA) в язык модели. Каждый feature должен иметь обоснование: «ACF показал лаг-24 → включаем lag_24h» или «оператор говорит, что ветер важен → но в данных ветра нет, используем proxy через HDD».

### Блоки роадмапы
- **3.1**: construct data — derived attributes
- **4.1**: распределения — проверить распределение новых features (нет ли бесконечностей, NaN после деления)
- **11.1**: time series — лаговые features, стационарность разностей

### Артефакт
- Feature Dictionary: таблица всех features с описанием, обоснованием, формулой
- Feature Pipeline: Python-код (функция/класс) который из raw data создаёт feature matrix

## Задача 3.4: Интеграция данных (Integrate Data)

### Что делаем

#### 3.4.1 Объединение источников

#### 3.4.2 Стратегия объединения подстанций (ключевое решение)

5 CSV файлов → как объединить? Три варианта:

| Вариант | Как | Плюсы | Минусы |
|---|---|---|---|
| **A: Одна модель** | Все подстанции в один DataFrame, substation_id как категориальный feature | Больше данных для обучения, одна модель для деплоя | Подстанции разные по размеру (L4=9135 м² vs L8=3801 м²), модель может быть suboptimal для малых |
| **B: Отдельные модели** | 5 отдельных моделей, каждая обучена на своей подстанции | Каждая модель адаптирована | Мало данных на L8/L12/L22 (10877 строк), 5 моделей поддерживать |
| **C: Кластерная** | Кластеризовать подстанции по EDA-профилям, одна модель на кластер | Баланс данных и адаптации | Сложнее, нужен обоснованный кластеринг |

**Решение принимается после EDA** на основе:
- Насколько похожи профили подстанций? (из задачи 2.3)
- Есть ли значимая разница в отопительных кривых? (t_sup_prim vs t_amb по подстанциям)
- Cross-validation: одна модель vs отдельные — что даёт лучший MAE?

**Предварительная рекомендация:** Вариант A (одна модель) для MVP — проще и больше данных. Вариант B — для сравнения. Зафиксировать решение и обоснование в Rationale for Inclusion/Exclusion.

### Для чего
Данные из разных источников (SCADA, метео, справочники) имеют разные форматы и ключи. Интеграция должна быть надёжной и воспроизводимой. Решение о способе объединения подстанций влияет на всю архитектуру моделирования.

### Артефакт
- Merged Dataset: единая таблица со всеми features и таргетом

### Чеклист готовности

## Задача 3.6: Train/Test Split (не из CRISP-DM — из ML практики)

### Что делаем

**КРИТИЧНО: для временных рядов НЕЛЬЗЯ делать random split. Только по времени.**

- Определить точку разделения: последний сезон = test, остальные = train
- Или: последние 20% времени каждой подстанции = test
- Validation: из train выделить последний период как validation (для hyperparameter tuning)
- Проверить: нет ли data leakage через границу split (лаги не заглядывают в test)

### Схема

```
|--- Сезон 1 ---|--- Сезон 2 ---|--- Сезон 3 ---|--- Сезон 4 ---|--- Сезон 5 ---|
|                    TRAIN                        |    VAL    |      TEST       |
```

Альтернатива — walk-forward (expanding window):
```
Fold 1: Train [S1]        → Test [S2]
Fold 2: Train [S1, S2]    → Test [S3]
Fold 3: Train [S1, S2, S3] → Test [S4]
...
```

### Для чего
Random split для TS создаёт data leakage: модель «видит» будущие значения через лаги. Только временной split гарантирует честную оценку. Walk-forward — золотой стандарт, но дороже вычислительно.

### Блоки роадмапы
- **3.1**: select data — train/test разделение
- **11.1**: time series — специфика split для TS

### Артефакт
- Train/Val/Test Sets: три файла или три DataFrame с записанными границами
- Split Documentation: какие даты в каком наборе, почему так

### Чеклист готовности
- [ ] Split выполнен ПО ВРЕМЕНИ (не random)
- [ ] Точка разделения train/test записана (конкретная дата)
- [ ] Точка разделения train/val записана
- [ ] Проверено: лаговые features на границе split НЕ заглядывают в test
- [ ] Размеры: train = X записей, val = Y, test = Z — записаны
- [ ] Каждый набор содержит достаточно данных (минимум 1 сезон в train, 1 месяц в test)

## Задача 3.7: Feature Pipeline (не из CRISP-DM — из MLOps)

### Что делаем
- Оформить весь код фазы 3 как воспроизводимый pipeline
- Функция/класс: raw_data → clean_data → features → train/val/test
- Параметризация: горизонт прогноза h, список лагов, окна rolling — как аргументы, не хардкод
- Тесты: unit-тесты для критичных функций (shift не в ту сторону = катастрофа)
- Версионирование данных: хэш или версия выходного датасета

### Для чего
Когда в фазе 4 вы начнёте экспериментировать с features (добавить/убрать), pipeline позволит быстро пересобрать данные. Без pipeline — ручная пересборка, ошибки, невоспроизводимость.

### Артефакт
- `feature_pipeline.py` — модуль с функциями/классами
- `config.yaml` или `params.py` — параметры (h, lags, windows)
- `tests/test_features.py` — минимальные тесты

### Чеклист готовности
- [ ] Pipeline запускается одной командой: `python feature_pipeline.py --horizon 6`
- [ ] Параметры вынесены в конфиг (не хардкод)
- [ ] Есть тест на data leakage: assert features.index < target.index для каждой строки
- [ ] Есть тест на NaN: после pipeline нет неожиданных NaN (кроме head из-за лагов)
