## Задача 5.2: Backtesting — ретроспективная симуляция

### Что делаем
Модель «играет за оператора» на историческом test-сезоне: что бы она рекомендовала и сколько бы сэкономили.

### Сценарий backtesting
Для каждого часа test set:
1. Модель прогнозирует T_return(t+6h)
2. Если прогнозируемый T_return > guardrail + margin → текущий режим ОК
3. Если прогнозируемый T_return > нормы + Δ → «перетоп», модель рекомендует снизить T_supply на Δ°C
4. Считаем: сколько часов перетопа обнаружено, какая суммарная экономия
5. Проверяем: guardrail ни разу не нарушен (если нарушен — модель небезопасна)

### Метрики backtesting
| Метрика | Формула | Что показывает |
|---|---|---|
| Hours of detected overheating | count(T_return_pred > norm + Δ) | Объём потенциальной экономии |
| Total energy savings (kWh) | Σ(c_p × ṁ × ΔT_recommended × 1h) | Суммарная экономия |
| Cost savings (руб) | Total energy × 1.6 руб/кВтч | Деньги |
| Guardrail violations | count(T_return_pred - MAE < T_min) | Безопасность (должно = 0) |
| False alarm rate | count(recommended reduction but no overheating) / total | Доверие оператора |

### 5.2.2 Попериодный backtesting (из Нетбая)

Нетбай (2020, Таблица 2) разбил тестовый месяц на периоды с резкими изменениями погоды и показал поведение модели в каждом. Повторяем этот подход:

**Разбить test set на характерные режимы:**

| Режим | Критерий | Что проверяем |
|---|---|---|
| Резкое похолодание | ΔT_amb < -5°C за 6ч | Модель повышает T_supply заранее? (как у Нетбая: +8°C) |
| Стабильный холод | T_amb < -15°C, ΔT_amb < 2°C | Модель держит стабильный режим? |
| Оттепель | ΔT_amb > +5°C за 6ч | Модель снижает T_supply быстрее оператора? |
| Пуск системы | delta_e: 0 → >0 | Модель адекватна при переходном режиме? |
| Останов системы | delta_e: >0 → 0 | Корректное поведение при отключении? |
| Малая нагрузка | delta_e < median × 0.3 | Точность при низком потреблении? |

**Для каждого режима:**
- Средняя ошибка (MAE) — отдельно
- Направление ошибки: модель перетапливает или недотапливает?
- Экономия/потери в рублях — отдельно
- Визуализация: один характерный период (2-3 дня) с аннотациями

**Итоговая таблица** (аналог Таблицы 2 Нетбая):
| Период | Средняя T_amb | T_pred в домах | Отклонение от факта | Экономия/потери |

### 5.2.3 Simulation Backtesting — Digital Twin теплосети

Обычный backtesting: модель прогнозирует T_return, сравниваем с фактом. Но модель не УПРАВЛЯЕТ — она только смотрит на прошлое.

Simulation backtesting: модель прогнозирует → рекомендует изменить T_supply → **симулятор пересчитывает** что произойдёт с домами → модель видит результат своего решения. Замкнутый цикл управления.

#### Зачем (ценность для портфолио и бизнеса)
- Backtesting отвечает: «модель точна?» Симулятор отвечает: «управление работает?»
- Показывает системное мышление — не «натренировал модель», а «построил среду и проверил управление»
- Digital Twin — актуальный тренд 2024-2026 в вакансиях DS/MLE
- Открывает дверь к Reinforcement Learning (опционально)
- Нетбай (2020) показал демонстрацию на реальных данных, но без замкнутого цикла — HeatWin идёт дальше

#### Уровень 1: Lookup-симулятор (MVP)

Принцип: при запросе «что будет если T_supply=80 при T_outdoor=-10?» находим ближайшие реальные ситуации в исторических данных и возвращаем реальный T_return.

```python
def simulate_lookup(T_supply_new, T_outdoor, history_df, k=5):
    """Найти k ближайших исторических ситуаций, вернуть median T_return."""
    distances = (
        (history_df["t_sup_prim"] - T_supply_new) ** 2 +
        (history_df["t_amb"] - T_outdoor) ** 2
    )
    nearest = history_df.nsmallest(k, distances.name)
    return {
        "T_return_predicted": nearest["t_ret_sec"].median(),
        "delta_e_predicted": nearest["delta_e"].median(),
        "confidence": nearest["t_ret_sec"].std(),  # чем меньше — тем увереннее
    }
```

Плюсы: быстро, не требует отдельной модели, результаты = реальные данные.
Минусы: не может экстраполировать (если T_supply=120 никогда не было — не знает).

#### Уровень 2: ML-симулятор (полный Digital Twin)

Обучаем ОТДЕЛЬНУЮ модель — модель среды (environment model):
- **Вход:** T_supply(t), T_outdoor(t), текущее состояние сети (T_return(t), delta_e(t))
- **Выход:** T_return(t+1h), T_return(t+3h), T_return(t+6h), delta_e(t+1h)
- **Обучение:** на тех же данных XAI4HEAT, но другой таргет (не прогноз, а реакция среды)

Замкнутый цикл:
```
Шаг 1: Прогнозная модель HeatWin: "рекомендую T_supply = 82°C"
Шаг 2: Симулятор: "при T_supply=82 и T_outdoor=-10 → T_return будет 48°C через 3ч"
Шаг 3: HeatWin проверяет: 48°C ≥ T_min? Да → рекомендация ОК
Шаг 4: Симулятор обновляет состояние → следующий час
→ Повторить для всего test-сезона
```

#### Что измеряем в simulation backtesting

| Метрика | Что показывает |
|---|---|
| Cumulative energy savings (кВтч) | Сколько сэкономили за сезон при управлении по модели |
| Guardrail violations (count) | Сколько раз T_return < T_min (должно = 0) |
| Comfort stability (std T_return) | Насколько стабильна температура в домах |
| Response time to weather change | Через сколько часов модель компенсирует похолодание |
| Comparison: model vs operator | Бок-о-бок: что делала модель vs что делал оператор |

#### Интеграция в дашборд

Вкладка **«What-if Simulator»** в Streamlit:
- Слайдер: T_supply (60–110°C)
- Слайдер: T_outdoor (-25...+15°C)
- Кнопка: «Запустить симуляцию на 24ч»
- Вывод: графики T_return(t), delta_e(t) для текущих настроек vs рекомендация модели
- Оператор видит: «если сейчас снизить T_supply на 5°C → через 3ч T_return будет 46°C (норма 44°C) → безопасно, экономия X кВтч»

## Задача 5.3: Дизайн пилота — A/B (блок 8 роадмапы)

### Что делаем
Для пет-проекта — дизайн пилота на бумаге (не реальный запуск). Для реального проекта — план запуска.

### 5.3.1 Switchback A/B дизайн
- Классический A/B невозможен: одна котельная, нельзя разделить на control/treatment
- **Switchback**: чередование дней/недель — «с HeatWin» vs «без HeatWin»
  - Нечётные недели: оператор работает как обычно (control)
  - Чётные недели: оператор следует рекомендациям HeatWin (treatment)
- Или **по подстанциям** (если модель по подстанциям): L4 = treatment, L8 = control → через 2 недели меняем

### 5.3.2 CUPED — variance reduction (блок 8 роадмапы)
- T_outdoor как ковариата: energy_adjusted = energy - θ × (T_outdoor - mean(T_outdoor))
- θ = cov(energy, T_outdoor) / var(T_outdoor)
- Зачем: погода — главный confound. Без CUPED «тёплая неделя в treatment» выглядит как эффект модели
- CUPED снижает дисперсию → снижает MDE → быстрее обнаруживаем реальный эффект

### 5.3.3 Power analysis для пилота (блок 14.4)
- σ² = var(energy_adjusted) из backtesting
- MDE = 5% от baseline energy_per_HDD → конкретное число в кВтч
- n = число switchback-периодов, необходимых для power ≥ 80%
- Формула: n = 2 × (z_α + z_β)² × σ² / MDE²
- Результат: «для обнаружения 5% эффекта с power 80% нужно X недель пилота»
- Если X > 1 сезон → MDE нереалистичен → пересмотреть дизайн или ожидания

### 5.3.4 SRM check (Sample Ratio Mismatch)
- После пилота (для реального проекта): проверить, что число периодов в control ≈ treatment
- Если нет — bias, результаты невалидны
- χ²-тест: H₀ = 50/50 split → шаблон 14.1

### Блоки роадмапы
- **8.1**: A/B дизайн — switchback, рандомизация
- **8.2**: CUPED — variance reduction через ковариату
- **8.3**: SRM — Sample Ratio Mismatch
- **14.4**: power analysis — MDE, n, power

## Задача 5.4: Причинный анализ (блок 10 роадмапы)

### Что делаем

#### 5.4.1 DAG — причинный граф (блок 10.1)
Формальный причинный граф системы теплоснабжения:

```
T_outdoor → T_supply_setpoint → T_supply → T_return ← building_mass ← HDD
    ↓                                          ↑
  wind_speed                              occupancy
    ↓                                          ↑
  heat_loss ──────────────────────────────→ energy
```

- Определить: что причина, что следствие, что confound
- Проверить: совпадает ли DAG с SHAP-результатами из фазы 4
- Если не совпадает — red flag: модель выучила spurious correlation

#### 5.4.2 DiD — эффект снятия шайб (блок 10.2)
Если в данных есть период до и после снятия дроссельных шайб:
- **Difference-in-Differences**: сравнить energy_per_HDD до и после снятия
- Treatment: подстанции, где сняли шайбы
- Control: подстанции, где не снимали (если такие есть)
- Если нет control → **прерванный временной ряд** (ITS) как альтернатива
- Результат: «снятие шайб изменило energy_per_HDD на X% (p = Y)»

#### 5.4.3 Ограничения причинного анализа
- SHAP ≠ причинность (зафиксировать в документации)
- DiD требует параллельных трендов (проверить визуально)
- Для реальной причинности нужен эксперимент (пилот) — наблюдательные данные дают только associaton + плausible causation

- **10.1**: DAG, d-separation, backdoor criterion
- **10.2**: DiD, параллельные тренды, ITS

## Задача 6.4: Мониторинг и обслуживание (Plan Monitoring)

### Что мониторим

| Метрика | Порог алерта | Действие |
|---|---|---|
| MAE rolling 7d | > 2.5°C (1.25 × target) | Проверить данные → переобучить |
| PI coverage 7d | < 85% (ниже target 90%) | Рекалибровать conformal scores |
| CUSUM на остатках | > control limit | Concept drift → переобучить |
| Input data freshness | > 2h без новых данных | Проверить SCADA → алерт |
| Feature distribution | KS-test p < 0.01 vs train | Data drift → проверить источник |

### Стратегия переобучения
- **Trigger**: CUSUM alert или MAE > threshold в течение 7 дней
- **Процедура**: запустить feature pipeline на новых данных → retrain → evaluate на hold-out → если лучше → заменить модель
- **Rollback**: если новая модель хуже — вернуть предыдущую (модели версионированы в MLflow)
- **Частота**: минимум 1 раз в сезон (даже без trigger) — seasonal retrain
