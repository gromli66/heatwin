Каждая фаза проекта — это не просто чеклист «сделай». Это набор вопросов, на которые нужно записать ответ. Ответы формируют отчёты.

## Фаза 1: Business Understanding

### 1.1 Determine Business Objectives — вопросы

**Организация:**
- [ ] Кто спонсор проекта? Кто принимает решения?
  → HeatWin: ООО «АТЭС-ПЗ» (для реального) / сам автор (для пет-проекта)
- [ ] Какие подразделения затронет проект?
  → Эксплуатация котельной, диспетчерская, руководство
- [ ] Знает ли бизнес о data mining? Нужно ли «продать» идею?
  → Для ПЗ: вероятно нет, нужна презентация концепции

**Проблемная область:**
- [ ] В чём проблема НА ЯЗЫКЕ КЛИЕНТА (не на языке DS)?
  → «Перерасход топлива из-за того что оператор не может заранее знать как изменится погода»
- [ ] Какое ТЕКУЩЕЕ решение и почему оно не устраивает?
  → Ручное управление каждые 2ч по текущему термометру; перетоп 5-15%
- [ ] Кто конечный пользователь результата?
  → Оператор котельной (дашборд), руководство (отчёт экономии)

**Цели:**
- [ ] Какова ГЛАВНАЯ бизнес-цель? (одно предложение)
  → Снизить расход топлива на 5-15% через прогнозное управление температурой
- [ ] Какие СОПУТСТВУЮЩИЕ вопросы клиент хочет решить?
  → Стабильность температуры в домах, уменьшение ночных вызовов оператора, обоснование для модернизации
- [ ] Как ИЗМЕРИТЬ успех? (критерий, который бизнес понимает)
  → Экономия в рублях за сезон, число эпизодов недотопа = 0

### 1.2 Assess Situation — вопросы

**Ресурсы:**
- [ ] Какие данные доступны? Где хранятся? Кто владелец?
  → XAI4HEAT (Mendeley, публичный), SCADA 5 подстанций 5 сезонов
- [ ] Какое оборудование? Есть ли GPU?
  → Ноутбук, CPU-only достаточно для LightGBM
- [ ] Кто доменный эксперт? Можно ли задавать вопросы?
  → Для пет-проекта: статья Нетбая + XAI4HEAT статья Cvetković = заменяют эксперта

**Допущения (ЗАПИСАТЬ — самое важное!):**
- [ ] Какие допущения о данных? (проверяемые в ходе проекта)
  → Данные XAI4HEAT репрезентативны, t_ret_sec < t_sup_sec при работе, инерционность 3-6ч
- [ ] Какие допущения о бизнесе? (НЕпроверяемые — от них зависит валидность)
  → Прогнозное управление лучше реактивного, оператор будет доверять рекомендациям, экономия переносима из Ниша в ПЗ
- [ ] При каких условиях результаты проекта НЕВАЛИДНЫ?
  → Если теплосеть ПЗ принципиально отличается от Ниша (масштаб, топология, климат)

**Ограничения:**
- [ ] Есть ли правовые ограничения на использование данных?
  → XAI4HEAT CC BY-NC — можно для исследований, нельзя коммерчески
- [ ] Какие технические ограничения?
  → Нет GPU, нет real-time данных для online-обучения
- [ ] Каковы сроки?
  → Пет-проект: ~200 часов, без жёсткого дедлайна

### 1.3 Determine DM Goals — вопросы

- [ ] Как БИЗНЕС-цель переводится в ТЕХНИЧЕСКУЮ?
  → Бизнес: «снизить перетоп» → Техника: «предсказать T_return на 6ч с MAE < 2°C»
- [ ] Какой ТИП задачи data mining?
  → Prediction (regression) на временных рядах = forecasting
- [ ] Как ИЗМЕРИТЬ техническую успешность?
  → MAE < 2°C, PI coverage ≥ 90%, R² > 0.85
- [ ] ОТЛИЧАЕТСЯ ли технический критерий от бизнес-критерия?
  → Да! MAE < 2°C ≠ экономия 5%. Нужен backtesting для перевода.

### 1.4 Produce Project Plan — вопросы

- [ ] Какой порядок шагов? Где возможны итерации?
  → CRISP-DM: возврат из Modeling в Data Preparation — частый сценарий
- [ ] Какое распределение усилий?
  → Data Prep 50-70%, Data Understanding 20-30%, Modeling 10-20%, Deployment 5-10%
- [ ] Какие инструменты выбраны и ПОЧЕМУ?
  → Python + LightGBM (быстрый, не требует GPU, feature importance) + Pandera + DVC
- [ ] Каковы критические точки принятия решений?
  → Gate review 2→3, выбор модели в фазе 4, решение deploy/iterate в фазе 5

## Фаза 2: Data Understanding

### 2.1 Collect Initial Data — вопросы
- [ ] Все ли нужные данные получены?
  → Да: 5 CSV + heating_areas

- [ ] Какие типы атрибутов? (числовые, категориальные, временные)

- [ ] Что означает каждый атрибут В БИЗНЕС-ТЕРМИНАХ?

- [ ] Удовлетворяют ли данные требованиям проекта?

- [ ] Используется ли значение атрибута СОГЛАСОВАННО?

### 2.3 Explore Data — вопросы
- [ ] Каковы распределения ключевых атрибутов?
  → Ответ после EDA: гистограммы + тесты (Shapiro-Wilk)
- [ ] Есть ли СВЯЗИ между парами атрибутов?

- [ ] Какие характеристики ПОДГРУПП?
  → По подстанциям: L4/L17 крупнее (9128-9135 м²), L8 наименьшая (3801 м²)
- [ ] Какие ГИПОТЕЗЫ формулируются?
  → Лог гипотез: наблюдение → тест → действие для моделирования
- [ ] Какова ИНЕРЦИОННОСТЬ системы?
  → Измерить cross-correlation (задача 2.3.7), записать lag в часах

### 2.4 Verify Data Quality — вопросы
- [ ] Данные ПОЛНЫЕ? Все ли случаи покрыты?
  → 5 подстанций, 3-5 сезонов. Летних данных нет (и не нужно)
- [ ] Данные КОРРЕКТНЫЕ? Есть ли ошибки?

- [ ] Есть ли ПРОПУСКИ? Как представлены?
  → Статья: данные предобработаны, пропусков нет. delta_e = 0 = система отключена (не пропуск)
- [ ] Какие РЕШЕНИЯ по проблемам качества?
  → L22: исключить или заменить t_amb. delta_e < 31 заменены на 0 (из статьи)

- [ ] В каком ПОРЯДКЕ записи?

## Фаза 4: Modeling

### 4.1 Select Technique — вопросы
- [ ] Какие ДОПУЩЕНИЯ у каждой техники?
  → OLS: линейность, нормальность остатков. LightGBM: нет строгих. LSTM: стационарность
- [ ] Выполняются ли эти допущения на НАШИХ данных?
  → Проверить в Data Description Report. Если нет → вернуться в Data Prep
- [ ] Есть ли ПОЛИТИЧЕСКИЕ/БИЗНЕС ограничения на выбор?
  → Понятность для оператора (SHAP нужен), скорость inference (LSTM медленнее)

### 4.2 Generate Test Design — вопросы
- [ ] Как РАЗДЕЛИТЬ данные на train/val/test?
  → Walk-forward по сезонам (phase4 задача 4.2)
- [ ] Какая МЕТРИКА качества?
  → MAE (основная), RMSE, R², PI coverage
- [ ] Сколько ИТЕРАЦИЙ/FOLD'ОВ?
  → Expanding: 3 fold'а + final test. Sliding: 2 fold'а + final test

### 4.3 Build Model — вопросы
- [ ] Какие ПАРАМЕТРЫ выбраны и ПОЧЕМУ?
  → MLflow: каждый run с обоснованием параметров
- [ ] Как ИНТЕРПРЕТИРОВАТЬ модель?
  → SHAP: summary, dependence, waterfall. Перевод в язык оператора
- [ ] Есть ли ТРУДНОСТИ с интерпретацией?
  → Если SHAP противоречит domain knowledge → red flag

### 4.4 Assess Model — вопросы
- [ ] Модель ПРАВДОПОДОБНА?
  → SHAP vs domain knowledge: t_amb должен быть важен, если нет — проблема
- [ ] Модель НОВАЯ/ПОЛЕЗНАЯ? (vs baseline)
  → DM-test: LightGBM vs ARIMA. Если нет значимой разницы — features не работают
- [ ] Модель НАДЁЖНА?
  → CI для MAE через bootstrap. Conformal PI для предсказаний
- [ ] Какой ПОТЕНЦИАЛ ДЕПЛОЯ?
  → Inference time, размер модели, зависимости

# 2. РИСКИ МОДЕЛИРОВАНИЯ (что может пойти не так при обучении)

Дополнение к project_brief_supplement.md (R1-R7 — бизнес/организационные).
M1-M10 — технические риски моделирования.

| # | Риск | Вероятность | Влияние | Как обнаружить | Что делать |
|---|---|---|---|---|---|
| M1 | **Data leakage в features** — лаги вычислены неправильно, модель «видит» будущее | Средняя | Критическое | MAE на train ≈ 0 при MAE на test >> 0; Walk-forward CV покажет деградацию | Проверить каждый lag вручную: T_return_lag_6h(t) = T_return(t-6), НЕ T_return(t+6). Unit-тест на shift direction |
| M2 | **Модель выучила сезонность, не физику** — предсказывает «ноябрь = 55°C» без связи с t_amb | Средняя | Высокое | SHAP: calendar features (month, day_of_year) в top-3, а t_amb внизу | Убрать calendar features, переобучить. Если MAE не меняется — модель ок. Если ухудшается — сезонность нужна, но проверить нет ли leakage |
| M3 | **Walk-forward CV хорош, реальный поток плох** — модель обучена на «чистых» данных, а реальные с шумом и задержками | Низкая (для пет) | Высокое (для production) | При деплое: MAE мониторинг. Если MAE на реальных > 1.5× MAE на test | Добавить noise augmentation при обучении, retrain на реальных данных |
| M4 | **SHAP противоречит domain knowledge** — модель говорит «t_amb не важен» при том что физика говорит обратное | Средняя | Высокое | SHAP summary plot: t_amb low importance | Red flag. Проверить: (1) нет ли мультиколлинеарности t_amb с t_ref (уставка = f(t_amb)), (2) нет ли ошибки в данных. Если причина найдена — ок. Если нет — модель ненадёжна |
| M5 | **Overfitting на конкретном сезоне** — модель идеально предсказывает зиму 2022-23, но не 2023-24 | Высокая | Высокое | Walk-forward: MAE сильно скачет между fold'ами (high variance) | Больше регуляризация (max_depth↓, min_child_samples↑), early stopping, feature selection |
| M6 | **LightGBM не бьёт ARIMA** — features не добавляют информации сверх автокорреляции | Средняя | Высокое | DM-test ARIMA vs LightGBM: p > 0.05 (нет значимой разницы) | (1) Пересмотреть features — возможно лаги недостаточны (2) Попробовать другие features: ΔT, скользящие средние, взаимодействия (3) Если ничего не помогает — ARIMA + exogenous (ARIMAX) как компромисс |
| M7 | **Лучшая модель непонятна оператору** — «чёрный ящик» вызывает недоверие | Средняя | Среднее | Feedback оператора (при реальном деплое) | SHAP waterfall для каждого предсказания: «модель считает T_return будет высокой потому что...». What-if слайдер в дашборде |
| M8 | **Conformal PI слишком широкие** — покрытие 90% достигнуто, но интервал ±8°C = бесполезно | Средняя | Среднее | Средняя ширина PI > 2 × MAE | Калибровать на большем val set, попробовать adaptive conformal (ширина зависит от уверенности), или признать: для данного горизонта точность модели недостаточна |
| M9 | **Разные подстанции требуют разных моделей** — одна модель плохо работает для L8 (малая подстанция) | Средняя | Среднее | MAE по подстанциям: разброс > 50% (например L4 MAE=1.2, L8 MAE=3.5) | Перейти к отдельным моделям (стратегия B из задачи 3.4) или добавить interaction features substation × temperature |
| M10 | **Переходные режимы (пуск/останов) — модель ошибается** — при delta_e: 0→>0 модель не успевает | Высокая | Среднее | Попериодный backtesting (задача 5.2.2): MAE при пуске >> MAE при стабильной работе | Отдельный флаг transition_mode, отдельная модель или правило для переходных режимов, или бо́льший margin в guardrail при пуске |
| M11 | **Digital Twin симулятор неточен** — ошибки среды накапливаются при многошаговой симуляции (error compounding) | Средняя | Среднее | Сравнить: simulation backtesting vs обычный backtesting. Если расхождение > 20% — симулятор ненадёжен | Ограничить горизонт симуляции (не 24ч подряд, а 6ч → reset из реальных данных). Или использовать только lookup-симулятор (уровень 1 — реальные данные, нет compounding) |

## 3.1 Data Description Report (фаза 2, задача 2.2)
